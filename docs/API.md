### HTTP API

JSON wire format (ISO-8601 timestamps); payload types in `packages/shared`. Each route
file maps to a `client.ts` method.

**`?workspace=<integer>` is THE scope parameter, everywhere.** It replaced `?scope=` and its five
`TeamScope` wire forms (`all` / `none` / `teams` / `teams:2,4` / `<id>`) with one integer, and there
is no parser, no canonicalisation and no sentinel.

- **Absent, unknown, unparseable, or another tenant's id ⇒ the account's DEFAULT workspace. Not a
  404.** Every id yields the same response shape (so it is not an existence oracle), the resolved id
  is always one the caller owns (so nothing can leak), and a stale bookmark degrades to something
  renderable instead of a blank screen. **Every scoped response echoes `workspaceId`** so the SPA
  can correct its stored id.
- `?repoIds=<csv>` survives as **data narrowing only** — the workspace owns the verdict, so the old
  "one selection cannot mean two things" hazard is structurally gone. But it is **BOUNDED**:
  `resolveWorkspaceScope` returns `membership ∩ (narrow ?? membership)`. Without that,
  `?workspace=5&repoIds=<a repo of workspace 9>` passes the account check, enumerates footprints
  over workspace-9 repos while the lazy classifier writes rows keyed to workspace 5 for actors with
  ZERO footprint there — fabricating exactly the rows `verify:isolation`'s anti-fabrication pair
  forbids. Doing it in one resolver is what stops it being a convention 14 handlers must remember.
- ⚠ **Five CONTENT routes take it too, and they never took `?scope=`**: `/api/timeline`,
  `/api/activity`, `/api/activity/feed`, `/api/open-prs`, `/api/branch-status`. `repoIds` alone was
  enough only while `null` meant "every repo of the account" — a workspace with **zero repos** gives
  `repoIds: []`, every client builder used to drop an empty array, and the server then returned the
  whole account: the precise opposite of "this workspace is empty". Hence also the client rule
  **`if (ids) p.set('repoIds', …)`**, not `if (ids && ids.length > 0)`, and a `ws:<id>` segment on
  every one of those React Query keys (two workspaces sitting on `repoIds = null` otherwise produce
  an identical query string and share a cache slot).

| Method & path | Purpose |
|---|---|
| `GET · POST /api/workspaces` · `PATCH · DELETE /api/workspaces/:id` · `POST /api/workspaces/:id/repos` | **Workspaces** (CORE) — the app's only scope. `GET` ensures the Default row + repairs missing memberships first → `WorkspacesResponse`. `POST {name}` always creates `isDefault:false`; a duplicate name 400s. `PATCH {name?, repoIds?}` — `repoIds` is the workspace's EXACT membership: ids ADDED are moved in, ids DROPPED go to Default via `rehomeReposToDefault`. A move is **membership and nothing else** — there is no second visibility axis to write. Renaming the Default IS allowed. `DELETE` → 204, but **409 `{error:'DefaultWorkspace'}`** on the default row; it re-homes the workspace's repos **and its `workspace_reviewers` rows** to Default inside one transaction before deleting. `POST /:id/repos {repoId}` MOVES one repo in. ⚠ There is **no `DELETE /:id/repos/:repoId`** — a repo is always in exactly one workspace, so "remove" is "POST it to Default". Tier `read` (matched explicitly in `tierFor`, so the choice is recorded rather than inherited) |
| `GET /api/timeline?workspace&from&to&repoIds&userIds&types&statuses&reviewStates&excludeBots` | **lean** feed `{prs[],events[]}` — no bodies/diffs. The window is CLAMPED to `config.retentionDays` and both selects are ROW-CAPPED (5k PRs / 20k events, newest-first) returning `truncated?: true` — unbounded dates used to materialise the whole retained dataset in one response. Defaults: 14d; the SPA sends `excludeBots=true` by default (toggle in Members; the omitted-param server default stays include). `excludeBots` hides the UNION set — `users.isBot` ∪ the resolved workspace's automated-reviewer verdict, a workspace manual "human" un-hiding both ways — minus `allowBotIds`. `reviewStates` filters `review_submitted` markers by verdict (approved/changes_requested/commented/dismissed); absent = all, empty = none |
| `GET /api/prs/:id` | full PR detail (threads, reviews, comments, commits, checks, labels) |
| `POST /api/prs/:id/refresh {wait?}` | **live PR-detail freshness** → `PrRefreshResponse {synced, changed, updatedAt}`. The SPA polls it every ~5s while a PR pane is open AND visible (`usePrLiveRefresh`); the header Refresh button posts `{wait:true}`. The poll is **probe-gated** (`sync/refresh-pr.ts`): a conditional REST GET of the PR 304s for free on a quiet tick, and only a 200 — or the ~30s forced-walk floor, there because CI-finish/thread-resolve never bump `updated_at` — pays for a `syncOnePr` walk (+ hydration bust BEFORE responding, the resync-after-write order rule). `changed` means "invalidate your caches": `updatedAt` moved, or a floor-forced/manual walk refreshed hydration-only detail (checks). `wait:true` = unconditional bust + `waitForInFlight` (the post-write-resync composition). A sync failure is `200 {synced:false}` — NEVER a 5xx (the stored PR is still valid; the client shows a stale note, not an error). POST (not GET) so the cross-origin guard applies; account-scoped → 404. Tier `prDetail` (pinned in `rate-limit.test.ts` — same GitHub-cost profile as `GET /api/prs/:id`) |
| `POST /api/prs/:id/mark-viewed` (alias `/dismiss`) | record a view (`sha?` defaults to head) → clears new-since badges |
| `GET /api/prs/:id/merge-options` | what the merge control needs, fetched LAZILY (the hot detail path must not wait on GitHub): repo-allowed methods + live mergeability + `mergeQueue` (null unless the base branch really has one — `enabled:false` would make every repo render a queue section) + `autoMerge{allowedByRepo,armed}`. The queue probe is `.catch(() => null)` — best-effort, never fails the control. Up to five upstream calls, so it shares the `prDetail` rate-limit tier with `GET /api/prs/:id` (and `…/files`) |
| `POST · DELETE /api/prs/:id/merge-queue` | enqueue / dequeue on **GitHub's native merge queue** → `MergeQueueResult`. WRITE+ re-checked; enqueue pins the LIVE head sha (same consent anchor as a merge), 400s when the base branch has no queue (rather than failing opaquely inside GraphQL), and is idempotent both ways. GraphQL-only — see `github/mutations.ts` |
| `POST · DELETE /api/prs/:id/auto-merge {mergeMethod,updateStrategy?}` | arm / disarm Pierre's own **"merge when ready"** → `ArmedMergeRequest` · 204 (idempotent). Arming re-checks WRITE+, refuses a non-open PR (409), pins the LIVE head sha (never the synced one — a stale pin disarms itself on the first tick), 409s `StaleBase` when the synced base ref no longer matches GitHub's, and probes the merge queue (best-effort): a queue on the base ⇒ the intent is stamped `viaMergeQueue` (the watcher ENQUEUES instead of direct-merging), a PR already IN the queue ⇒ 409 `AlreadyQueued` (it is already landing). Disarm with the watcher's own queue entry live (`enqueuedAt` set) also best-effort dequeues it — "cancel" must not leave the queue to land the PR anyway; the row is deleted FIRST so the cancel wins even if the dequeue fails. TTL 72h. The arm response is the FULL row (identity + `phase:'pending_first_check'`), so the SPA can seed its progress card on the click rather than on the next poll |
| `GET /api/auto-merge` | every armed (+ resolved within 24h, cap 200, newest first) intent for the account → `ArmedMergeListResponse`. A pure DB read — the SPA POLLS it for the "it landed" toast and the cross-PR progress stack, so it must never touch GitHub. Each row is SELF-DESCRIBING: `repoOwner`/`repoName`/`prNumber`/`prTitle` (joined, so a global card can label a row without a second request per PR) plus `phase` — the machine-readable twin of the prose `lastReason`, non-null only while ARMED (terminals read `state`; null = a wait the watcher can't characterise). See docs/MERGE-CI-TRUNK.md |
| `GET /api/prs/:id/checks/:jobId/logs?tail` \| `?startByte&endByte` | a live WINDOW of an Actions job log (never stored) → `CheckLogsResponse`. Offsets are SOURCE bytes (the `\r\n` normalisation is display-only), `endByte` EXCLUSIVE, `hasMore` = "more exists ABOVE this window" — so feeding a response's `startByte` back as the next `endByte` abuts exactly. Every path is capped at `MAX_LOG_BYTES` (8 MiB) via a rolling buffer (~2×cap peak) even when the source ignores `Range`. Serves PASSING checks too — see **Merge, CI logs & trunk status** |
| `GET /api/branch-status?workspace&repoIds` | **default-branch health** per repo in scope → `BranchStatusResponse` (head snapshot + failing checks + `mergedPrs`: the ≤10 most recently MERGED PRs, merge order, each CONSOLIDATING its retained trunk commits — `{prNumber, prId, title, author, mergedAt, ciStatus (its newest commit's), commits[{sha, messageHeadline}]}`; direct pushes are chart-only, never listed. `prId`/`title` null when the PR isn't synced for this account — the client links out to github.com. `mergedAt` falls back to the newest consolidated commit's time when unresolved, so merge ordering is total). Pure DB read off what the branch sync persisted — never a live GitHub call, hence the plain `read` tier. Repos with nothing synced still appear, with nulls. **Informational only:** nothing here feeds attention counts, badges or My Turn |
| `GET /api/branch-trends?repoId` | **per-repo trunk trend series** → `BranchTrendsResponse`: ONE per-UTC-day array `daily: {day, failed, passed, merged}[]` on a SHARED axis — `failed` = trunk commits with a red rollup that day, `passed` = commits with a 'success' rollup (pending/unknown are neither), `merged` = PRs merged into the default branch that day (`baseRefName = defaultBranchName`, NULL base excluded; blind to direct pushes by construction). Dense from the OLDEST RETAINED commit day, not padded to 90d (the 100-commit cap can trim inside the date window); the merged line truncates to the SAME span on purpose — alignment is the point. Rendered as the Bot-Behaviour "Daily coverage" layout (`DayStrip`: cells split red-over-green by failed/passed share, opacity ∝ the day's total, + the merged-PRs line band). Pure DB read, `read` tier. **Lazy by contract**: fetched only when a `BranchStatusPanel` row is EXPANDED (`useBranchTrends(repoId, open)`) — never inline on `/api/branch-status`, which is a hot workspace-wide path refetched every Feed render. `repoId` is ownership-scoped → 404 |
| `GET /api/prs/:id/ml-labels` | **THE per-PR ML-label index** → `PrMlLabelsResponse` (severity `nit|minor|major|critical` + the eight-value category list, per target). Every badge on the page reads this ONE query (React Query dedupes it; `staleTime: Infinity`), so a 60-thread PR costs one request, not 60 — a target with no label is simply absent from the array. Pure DB read: the model is only ever called by the background worker (`sync/ml-enrichment.ts`), never on a request, so this can never spend anything. Ownership 404 via the getter. Registered in EVERY mode — with no `SEVERITY_API_URL` it just returns an empty set rather than 404ing, and the SPA gates on `MeResponse.mlSeverity`. Rate tier `read`, **recorded rather than inherited** because it sits inside the `/api/prs/<id>/` family whose other members hydrate from GitHub. Detail: [ML-SEVERITY.md](ML-SEVERITY.md) |
| ~~`GET /api/feed`~~ | **DELETED** with `api/routes/feed.ts`. It was the superseded, account-wide mirror of `GET /api/activity/feed` and had NO caller left (the only reference anywhere was a stub in the e2e mock server). Its own header had carried the instruction — "if this endpoint ever gains a caller, scope it through `resolveWorkspaceScope` … or delete it" — and it never did: it predated workspaces, which also made it the last unscoped content route in the app. `getFeed` itself STAYS in `db/queries.ts`; `getConsolidatedFeed` calls it internally, which is where the workspace scoping and bot filtering are applied |
| ~~`GET /api/bot-severity`~~ | **DELETED** (the consolidation cut list). The standalone Bots-interface severity rollup had had no SPA consumer since the merged Bots ROI table took its severity columns off `/api/bot-analytics`'s windowed `ml` fold; keeping a corpus-wide, unwindowed twin of the same numbers alive "for back-compat" was one more predicate to hold in parity for zero renderers. `getBotSeverityRollup` itself STAYS in `db/ml-labels.ts` — its findings-only exclusion semantics are the documented reference the merged fold mirrors — only the route and client method are gone |
| `GET /api/ml-status` | **Live state of the enrichment worker** → `MlEnrichmentStatus` (`running`, `pending`, `labelled`, the current tick's `scoredThisRun`/`batchesThisRun`/`failuresThisRun`, `pausedUntil`, `serviceHealthy`, `markerFallback`). Exists so **the sync UI can represent the SECOND half of a sync**: the GitHub walk only stores the text, and the badges the board renders come from a model pass that runs after it — an indicator that stops at the end of the walk announces "complete" while the CPU is still working. **NO scope parameter, on purpose:** the worker walks every workspace of the account, so a workspace-scoped backlog would under-report exactly the work that is running. Pure read, nothing billable. ⚠ **Rate tier `search` (60/min), not `read`** — it is POLLED on a timer, and its backlog half is the severity rollup's unlabelled-count joins (`db/ml-labels.ts`) repeated per workspace; the handler additionally caches that scan ~3s per account, because a tier bounds request COUNT and not the work each one does. ⚠ Clients must not treat `pending > 0` alone as "scoring in progress" — see `isMlScoring` and the four stalled states in [ML-SEVERITY.md](ML-SEVERITY.md) |
| `POST /api/prs/:id/resolve-bot-threads {threadIds}` | **bulk-resolve** the review-bot threads a later commit likely addressed → `{resolved,failed,results[]}`. Server RE-DERIVES eligibility (owned + review-bot-originated + `likely_addressed`) ∩ the client's reviewed list, then GitHub-resolves each (shares the `bot-triage/resolve.ts` `resolveThreadsOnGitHub` helper with the scope-wide resolve route); never auto/blind — user-initiated + confirm-gated only. Core |
| `GET /api/bot-reviewers?workspace&repoIds` · `PATCH /api/bot-reviewers/:userId {workspaceId, automated?, role?, kind?, label?}` · `PUT /api/bot-reviewers/:userId/cost {workspaceId, monthlyUsd}` · `DELETE /api/bot-reviewers/:userId/judgement?workspaceId=` · `DELETE …/identity?workspaceId=` | **Bot-Triage** (CORE) — **ONE row, TWO write routes, TWO independent provenance flags.** The LISTING returns one `reviewers` entry per actor with a footprint in the workspace (each carrying judgement + identity + price + `footprint` + `repoFootprints[]` + `sampleReviewBody`) plus the echoed `workspaceId` and the `repoIds` it covered → `DetectedReviewersResponse` (`repoIds: []` means "this workspace has no repos", which a count alone could not distinguish from "no reviewers detected yet"). Its **lazy classification** fires on *an actor with a footprint in this workspace and no row for it* — one derivation per actor per workspace, not per repo. · **`PATCH :userId`** carries the four **re-derivable** fields in one body; all optional (absent = leave alone) but a body with NONE of them 400s (an opinion-free patch would stamp a provenance flag on an empty request and freeze detection). ⚠ **`automated`/`role` stamp `source:'manual'`; `kind`/`label` stamp `identitySource:'manual'` — INDEPENDENTLY.** That independence is the only thing left stopping "not a bot here" from also un-naming the vendor, now that no table boundary does it. ⚠ **A role-only patch still stamps `source:'manual'`**, pinning `automated` too — deliberate: not stamping it lets the next pass re-derive `role` from the login seed and silently revert the edit; a visible, resettable pin beats an edit that quietly disappears. ⚠ Its `set:` object contains **no `monthlyCents` key** — structural, not a rule to remember. · **`PUT …/cost {workspaceId, monthlyUsd}`** is now **PAID: it 402s without the `botDepth` entitlement** (the same `entitledProCapabilities` view `/api/me` serves — a bound-plugin local run is fully entitled, a free cloud account gets the same 402 shape as the plugin routes; the ONLY bot-reviewers route behind the check, classification/identity/role stay free). It stayed a SEPARATE route when the grains merged, and that is the point: cost is derivable by nothing and is money, so keeping it on its own body means no combined body can address the column at all — the same structural guarantee the two-table split gave, with one fewer table. `monthlyUsd` is REQUIRED and NULLABLE so `undefined` is not a third meaning: a number sets it (**0 is real** — "we pay nothing"), null CLEARS it — a column write, never a row delete. Bounds are NOT cosmetic: `[0, 21474836.47]` + `multipleOf:0.01`, the int4-cents ceiling where the dialects stop agreeing (pg RAISES `integer out of range`, sqlite accepts it) — ajv 400s, and the query layer clamps as the backstop. ⚠ It writes **exactly one row** (`(accountId, workspaceId, authorUserId)`): price is PER WORKSPACE. · **Two RESETS, one per provenance flag, and the asymmetry is gone — both are UPDATE + re-derive-in-the-same-request → 200 with the fresh row** (the old per-repo judgement reset DELETED its row and 204'd; that row now also holds the identity and the price, so a delete is lossy). `…/judgement` hands `automated`/`role`/`confidence`/`reasons` back to detection; `…/identity` clears `kind`/`label`, sets `identitySource:'auto'` and **KEEPS THE PRICE** (un-naming a vendor is not a statement about what it costs). ⚠ Both call `classifyReviewer(…, [workspaceId], {only:'judgement'\|'identity'})` — a REAL workspace id. The old identity reset passed an EMPTY repo list and relied on `persist` writing two statements against two TABLES with only the second guarded; with one merged row there is a single per-workspace loop, so an empty list writes NOTHING and "Reset name" becomes a permanent un-naming. ⚠ Order is load-bearing: clear BEFORE deriving, or `persist` skips the still-`manual` row. · **404 rules, one status for all of them, deliberately**: unknown user / unknown-or-foreign workspace / no stored row AND no footprint in that workspace — distinguishing them would be an existence oracle over another tenant's ids and the GLOBAL `users` table. ⚠ The PATCH's gate is `!existing && !hasFootprintInWorkspace(...)`, and the `!existing &&` half is load-bearing: a STORED row whose actor has gone quiet must stay editable, because it is still steering every metric and is the only place its own reset control can live |
| `GET /api/bot-analytics?window&workspace&repoIds[&fromMs&toMs]` | **Bot-ROI** (CORE): per-`AutomatedReviewerKind` volume/actedOn%/untouched/oldest/humanFollowThrough/noiseRatio/`verdict`(keep\|tune\|**noisy**) + ≤12wk trend + tuning suggestions → `BotAnalyticsResponse`. **Cost is SERVER-resolved from the workspace row** (`costMonthlyUsd` / `costPerActedOnUsd`, from `workspace_reviewers.monthly_cents` via `reviewerCostForUser(accountId, workspaceId)`) — a null here is FINAL. The client keeps a **null-only legacy fallback** (it fills a row ONLY where the server-resolved cost is null, badged `acct`) for logins the plugin's cost backfill could not attach to a bot row, since that migration only ever UPDATEs and never INSERTs. ⚠ **Never sum cost across WORKSPACES**: within this one workspace's rows it is a plain sum (one row per actor), but six workspaces each listing a $120 CodeRabbit is either six subscriptions or one seen six ways and the app must not assert which. **Role split:** the getter computes a row for EVERY automated reviewer, then routes `role:'quality_check'` ones into **`qualityChecks[]`** — same shape, kept OUT of `vendors`/`totals`/`suggestions` (a linter's volume must not move an acted-on % that claims to be about REVIEW throughput, and its untouched threads would earn a `noisy` verdict for doing its job), rendered as a collapsed "excluded from ROI" section so a mis-role is discoverable instead of the bot appearing to vanish. Classification is **workspace-resolved** from the route's own `?workspace=`, while `repoIds` narrows only the DATA — the two answer different questions and can no longer disagree (`BotScope {workspaceId, repoIds}` is one object with two named fields precisely so a call site cannot transpose them or forget which one the verdict comes from). **Response-time-gated verdict:** the verdict keys on `overdueUntouched` (untouched threads older than a **fixed 36h grace window**, `totals.overdueGraceMs`), NOT raw `untouched` — so a bot isn't flagged noisy for threads still inside the grace window. (A MEASURED reply-time norm was tried but the sample is intrinsically fast — only threads someone engaged with draw a reply — so a flat cutoff is the fair gate.) Each row also carries `medianAddressedMs` (that bot's own median **time-to-ADDRESSED** — the earliest of a human reply, a resolve, or the addressing commit for a `likely_addressed` thread, computed read-time from `commits`/`commitFiles` for just those threads' PRs; display-only). ('kill' was renamed 'noisy'.) Vendor rows carry `dormant`+`lastActiveAt`: ANY trend-span footprint (threads, comments, or body-only reviews) keeps a quiet reviewer visible as a DORMANT row (zeroed window counts + trend + last-active chip) instead of vanishing; body-only reviews count as window activity for emission/dormancy but never enter the volume math. **The WINDOWED ML label fold rides this response** (docs/ML-SEVERITY.md): per-vendor `mlFindings`/`mlBySeverity`/`mlNitPct`/`mlHighPct` (ABSENT — not zero — when the bot has no in-window labels; rates divide by FINDINGS, summaries+praise excluded; `vendorSeverity` is never an input) plus a response-level `ml` block (`BotAnalyticsMlTotals`: windowed totals, `byCategory`, windowed `pending`, `backends`, `truncated`) feeding the merged Bots table's severity columns + totals strip (`/api/bot-severity` is deleted — this fold is the one serving path). A **nit-ratio suggestion** joins `suggestions` (severity slot `'nit'`; gates: findings ≥ 20 AND nit share ≥ 0.7; skipped for quality checks). ⚠ **Those same gates now feed `botVerdict`** — one shared pair of constants, so the chip and the advisory cannot contradict each other — **escalating `keep` → `tune` only**: `tune`/`noisy` are never softened, a label can never produce `noisy`, the gate reads the RAW share not the rounded `mlNitPct`, and `vendorSeverity` is never an input (pinned by `bot-analytics-verdict.test.ts`; the fold by `bot-analytics-ml.test.ts`). Per-vendor `mergedPastPrs`/`mergedPastThreads` ("Merged past"): PRs MERGED inside the window still carrying ≥1 untouched thread by this bot at merge — the team's final answer was to ship anyway; keyed on the PR's `mergedAt` (a dedicated query, so the threads may be OLDER than the window and a dormant row can still be non-zero); display-only, `verdict` never reads them. Two more additive fields: per-vendor `notAddressedBySeverity` (the untouched threads split by the severity of the finding that OPENED each one — the label on the thread's first comment by its own bot; addressed threads, praise and summaries excluded; absent under the same rule as its `ml*` siblings, and ⚠ **it need not sum to `untouched`**, since an unscored opening comment counts there and nowhere here) and response-level `totals.overlapClusters` (DETERMINISTIC — the window's ±3-line clusters flagged by >1 review bot, counted ONCE; it is NOT the sum of the rows' `overlapThreads`, which credits every member). **Per-vendor `mlInflation`** (`BotVendorInflation` — the ROI table's Inflation column): current-window `overCall`/`underCall`/`agree` over that bot's BADGED findings (`vendorOverCall`/`vendorUnderCall` semantics — absent, NOT zero, for a bot that badges nothing: no badge is silence, not agreement). Its **`weekly` sparkline series (≤12 points) is ENTITLEMENT-GATED**: the route passes `inflationHistory` = the account's `botDepth` entitlement into `getBotAnalytics`, and an unentitled account simply gets no `weekly` key — hidden, never an error, and the current-window counts stay FREE (they are a verdict riding the already-free ML fold). **Optional explicit bounds `fromMs`/`toMs`** (epoch-ms digit strings, ajv-patterned, half-open `[fromMs, toMs)`) refine the enum into the apiVersion-18 `{kind, fromMs, toMs}` window form so the People report's bot sections can cover a COMPLETED period — an arbitrary-bounds period has no `BotWindowKind` spelling. `parseWindowBounds` (`api/routes/bot-triage.ts`) **400s** rather than degrading — only-together (half a pair is `'`fromMs` and `toMs` are only valid together'`), safe integers, `from < to`, span ≤ **200 days** (`WINDOW_BOUNDS_MAX_SPAN_MS`, mirroring the plugin's `PERSON_WINDOW_MAX_MS`) — because a bad bound is a client bug naming a POPULATION, not a stale bookmark; bounds carry no authority, they only narrow what is MEASURED inside the already-resolved scope. ⚠ **The fold honoured an explicit `toMs` in only TWO places** — the automated thread scan, `mergedPastRows`, `getMlWindowAggregates` and `countUnlabelledBotText` were `>= from` with no upper bound, so ONE ROW mixed two window populations. ⚠ **And the first fix was itself wrong**: `lt(col, to)` applied UNCONDITIONALLY excluded rows written in the CURRENT SECOND under the enum form (`to ≡ Date.now()`, second-granular columns on sqlite) and flaked `verify:isolation`. The rule is `const toBound = typeof window === 'string' ? null : to` — an upper predicate ONLY under explicit bounds, which also keeps every enum-form scan byte-identical to the drill-downs over the same rows (the "an Inflation count IS the drill-down's `filteredTotal`" identity). Explicit bounds are `lt`, never `lte` |
| `GET /api/bot-authoring?userId&fromMs&toMs&workspace&repoIds[&evidence=1]` | **Authoring-automation output** (CORE, FREE, deterministic, no AI) — the bot-shaped twin of the person vector, over `db/automation-output.ts` → `AutomationOutputResponse`.
