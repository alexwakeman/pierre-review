### HTTP API

JSON wire format (ISO-8601 timestamps); payload types in `packages/shared`. Each route
file maps to a `client.ts` method.

**`?workspace=<integer>` is THE scope parameter, everywhere.** It replaced `?scope=` and its five
`TeamScope` wire forms (`all` / `none` / `teams` / `teams:2,4` / `<id>`) with one integer, and there
is no parser, no canonicalisation and no sentinel.

- **Absent, unknown, unparseable, or another account's id ⇒ the account's DEFAULT workspace. Not a
  404.** Every id yields the same response shape (so it is not an existence oracle), the resolved id
  is always one the caller owns (so nothing can leak), and a stale bookmark degrades to something
  renderable instead of a blank screen. **Every scoped response echoes `workspaceId`** so the SPA
  can correct its stored id.
- `?repoIds=<csv>` survives as **data narrowing only** — the workspace owns the verdict, so the old
  "one selection cannot mean two things" hazard is structurally gone. But it is **BOUNDED**:
  `resolveWorkspaceScope` returns `membership ∩ (narrow ?? membership)`. Without that,
  `?workspace=5&repoIds=<a repo of workspace 9>` passes the account check, enumerates footprints
  over workspace-9 repos while the lazy classifier writes rows keyed to workspace 5 for actors with
  ZERO footprint there — fabricating exactly the rows `verify:isolation`'s anti-fabrication pair
  forbids. Doing it in one resolver is what stops it being a convention 14 handlers must remember.
- ⚠ **Five CONTENT routes take it too, and they never took `?scope=`**: `/api/timeline`,
  `/api/activity`, `/api/activity/feed`, `/api/open-prs`, `/api/branch-status`. `repoIds` alone was
  enough only while `null` meant "every repo of the account" — a workspace with **zero repos** gives
  `repoIds: []`, every client builder used to drop an empty array, and the server then returned the
  whole account: the precise opposite of "this workspace is empty". Hence also the client rule
  **`if (ids) p.set('repoIds', …)`**, not `if (ids && ids.length > 0)`, and a `ws:<id>` segment on
  every one of those React Query keys (two workspaces sitting on `repoIds = null` otherwise produce
  an identical query string and share a cache slot).

| Method & path | Purpose |
|---|---|
| `GET · POST /api/workspaces` · `PATCH · DELETE /api/workspaces/:id` · `POST /api/workspaces/:id/repos` | **Workspaces** (CORE) — the app's only scope. `GET` ensures the Default row + repairs missing memberships first → `WorkspacesResponse`. `POST {name}` always creates `isDefault:false`; a duplicate name 400s. `PATCH {name?, repoIds?}` — `repoIds` is the workspace's EXACT membership: ids ADDED are moved in, ids DROPPED go to Default via `rehomeReposToDefault`. A move is **membership and nothing else** — there is no second visibility axis to write. Renaming the Default IS allowed. `DELETE` → 204, but **409 `{error:'DefaultWorkspace'}`** on the default row; it re-homes the workspace's repos **and its `workspace_reviewers` rows** to Default inside one transaction before deleting. `POST /:id/repos {repoId}` MOVES one repo in. ⚠ There is **no `DELETE /:id/repos/:repoId`** — a repo is always in exactly one workspace, so "remove" is "POST it to Default". Tier `read` (matched explicitly in `tierFor`, so the choice is recorded rather than inherited) |
| `PUT /api/workspaces/:id/pending-mute` | **The Pending mute** (CORE). Body `{muted?, mutedRepoIds?}`, both optional; `{}` is a legal no-op. ⚠ **TWO INDEPENDENT FACTS, OR-ed, NEVER A CHAIN** — a repo is muted when the workspace switch OR its own row says so, and a key you OMIT is left alone (sending an unchanged half overwrites the other grain's stored value). `mutedRepoIds` is the EXACT muted set **within this workspace's membership**: ids outside it are IGNORED rather than 400'd, and rows for repos in OTHER workspaces are untouched — without that scoping a Save here would clear every mute set elsewhere, because the stored row is repo-grained and carries no workspace id. Ownership → 404; tenancy is additionally STRUCTURAL (composite FK on `(repo_id, account_id)`). Echoes the refreshed `{workspace}`, whose `pendingMuted` + `mutedRepoIds` are how the client reads the current state (there is no GET). ⚠ **It mutes nothing on screen**: the repo stays fully live everywhere and its items stay on the Pending board — `getMyTurn` downgrades their `relevance` to `'none'`, so they stop claiming the reader's turn, stop notifying and stop counting towards `myTurnPersonal`. Tier `read`, via the workspace-CRUD line in `tierFor` (pinned in `rate-limit.test.ts`) |
| `PUT /api/workspaces/:id/flow-settings` | **Chronology's working hours and wait budgets** (CORE). Body `FlowSettings` (`timeZone?`, `days?`, `startMinute?`+`endMinute?` as a pair, `budgets?.{firstLook,reply,land,lead}.{good?,ok?}`), every property declared in the ajv schema. ⚠ **PUT REPLACES THE WHOLE OVERRIDE SET** — a field left out goes back to its product default and `{}` stores NULL ("Reset to defaults"); the column holds overrides only and every reader resolves through `resolveFlowSettings` (`packages/shared/src/flow-settings.ts`). Meaning is checked by `validateFlowSettings`, the SAME function the Settings form runs, so the 400 `{error:'InvalidFlowSettings', message}` carries the sentence the reader would have seen inline. Ownership → 404. Echoes `{workspace}` (`Workspace.flowSettings`, raw overrides or null). Tier `read` (pinned in `rate-limit.test.ts`). See docs/BOTTLENECKS.md § Working hours |
| `GET /api/timeline?workspace&from&to&repoIds&userIds&types&statuses&reviewStates&excludeBots&prIds` | **lean** feed `{prs[],events[]}` — no bodies/diffs. The window is CLAMPED to `config.retentionDays` and both selects are ROW-CAPPED (5k PRs / 20k events, newest-first) returning `truncated?: true` — unbounded dates used to materialise the whole retained dataset in one response. Defaults: 14d; the SPA sends `excludeBots=true` by default (toggle in Members; the omitted-param server default stays include). `excludeBots` hides the UNION set `hiddenBotUserIds` — `users.isBot` ∪ `github_type='Bot'` ∪ the REVIEW_BOTS and `AUTOMATION_VENDORS` logins and prefixes (`db/automation-ids.ts`) ∪ the resolved workspace's automated-reviewer verdict, a workspace manual "human" un-hiding over every half — minus `allowBotIds`. `reviewStates` filters `review_submitted` markers by verdict (approved/changes_requested/commented/dismissed); absent = all, empty = none. **`prIds=<ids>`** (the SPA's pr-focus tab) returns exactly those PRs and ALL their events, and IGNORES every other param: no repo scope, no date window (the events select is still row-capped at 20k), no `types`/`userIds`/`statuses`/`reviewStates`/`excludeBots`/`allowBotIds`/`excludeStale`. Still `accountId`-scoped — a scope bypass, never a tenancy one. ⚠ The SPA sends it with NOTHING else (`buildTimelineSearch`'s early return, pinned by `apps/frontend/test/workspaceScope.test.ts`) and applies the Focus tab's Events and "Hide bots" controls CLIENT-side (`components/Timeline/isolateFilter.ts`): the request names no workspace, so a server-side `excludeBots` would judge bots by the account's DEFAULT workspace rather than the PR's own, and any extra param would re-key the query and refetch the PR on every toggle |
| `GET /api/prs/:id` | full PR detail (threads, reviews, comments, commits, checks, labels). `headRefName` / `baseRefName` are the synced branch names (`null` = not synced yet, never "no branch"). ⚠ **`reviewStandings` + `reviewerCount` are the SERVER's fold, not the client's** — `computeReviewStandingsByPr`, the same one the Pending card's chips and the hashed `approvals` count read (a reviewer's latest VERDICT, else their latest dismissal, else their latest comment). The pane used to fold `reviews` itself with "latest non-pending wins", which silently demoted an approver who later left a bare comment: 59 disagreeing reviewer-PR pairs on live open PRs. UNCAPPED here (the board caps at 5 and carries a `+N`); `reviewerCount` is the fold's own total and INCLUDES reviewers whose GitHub account is gone, who cannot be named in the list. ⚠ `inMergeQueue` / `mergeQueueEntryState` are SYNCED columns with the same three-state rule as the card's (`null` = NOT OBSERVED, never "not queued"), and they are also STAMPED by every path that holds a live answer about the queue (see the merge-queue rows below); position and ETA stay live-only on `…/merge-options`. **`threads[].limnSeverity` / `comments[].limnSeverity`** (optional, `LimnSeverity`: `blocker`·`warning`·`nit`·`question`) mark a thread or PR-level comment that is a finding LIMN POSTED, with the severity it was posted with (`db/limn-finding-severity.ts`: the finding's stored comment id → the thread's ROOT comment / the PR comment, its reminder's comment, else the shared `findFindingThread` matcher; severity through the grader seam `severityForPostedFinding`). Null on everything else and absent on every other thread surface; the pane's chip reads only this, never a fetch of its own |
| `POST /api/prs/:id/refresh {wait?}` | **live PR-detail freshness** → `PrRefreshResponse {synced, changed, updatedAt}`. The SPA polls it every ~5s while a PR pane is open AND visible (`usePrLiveRefresh`); the header Refresh button posts `{wait:true}`. The poll is **probe-gated** (`sync/refresh-pr.ts`): a conditional REST GET of the PR 304s for free on a quiet tick, and only a 200 — or the ~30s forced-walk floor, there because CI-finish/thread-resolve never bump `updated_at` — pays for a `syncOnePr` walk (+ hydration bust BEFORE responding, the resync-after-write order rule). `changed` means "invalidate your caches": `updatedAt` moved, or a floor-forced/manual walk refreshed hydration-only detail (checks). `wait:true` = unconditional bust + `waitForInFlight` (the post-write-resync composition). A sync failure is `200 {synced:false}` — NEVER a 5xx (the stored PR is still valid; the client shows a stale note, not an error). POST (not GET) so the cross-origin guard applies; account-scoped → 404. Tier `prDetail` (pinned in `rate-limit.test.ts` — same GitHub-cost profile as `GET /api/prs/:id`) |
| `POST /api/prs/:id/mark-viewed` (alias `/dismiss`) | record a view (`sha?` defaults to head) → clears new-since badges |
| `GET /api/prs/:id/files` | the Changes tab's per-file patches, a LIVE GitHub read (never stored) → `PrFilesResponse {files, truncated, headSha, nextPage, ceilingReached}`. `?page=N` (1-30) is the "Load next 100 files" click — ONE REST page of 100 per request, never on mount; `nextPage` is set whenever the page came back full, `ceilingReached` when page 30 was full (GitHub lists at most 3,000 files). Page 1 stays the persisted `['pr-files', id]` key; later pages live under the unpersisted `['pr-files-more', id, headSha, startPage]` infinite query. `headSha` is the STORED head at this read: the SPA keeps the diff at `staleTime: Infinity` and refetches it when a PR detail read AFTER it names another head (`prFilesOutdated`, `hooks/usePr.ts`), so a push reaches the tab. A GitHub failure degrades to `{files: [], truncated: false, headSha: null}` (never a 500), and `null` makes the next newer detail retry it. Rate tier `[pr_detail, read]` |
| `GET /api/prs/:id/files/content?path=&side=head\|base` | a gap marker's "Show N hidden lines" (CLICK-GATED, never on mount, never stored) → `PrFileContentResponse {path, side, sha, lines, refused}`. `side=head` reads the STORED head; `side=base` the merge base (`compare` of the PR's base SHA against the head — 1 `pulls` + 1 `compare` call, cached IN MEMORY per `(accountId, prId, headSha)`). `refused`: `too_large` (over ~1 MB, cut while reading), `binary` (a NUL byte), `missing` (404 at that commit). `path` must be repo-relative (no `..`, leading `/`, `\\` or NUL → 400); owner/name come from the account-scoped PR row, so another account's PR 404s before any GitHub read. GitHub failure → 502. The SPA refuses to splice lines that disagree with the patch (`patchMatchesFile`). Rate tier `[pr_detail, read]` |
| `GET /api/prs/:id/files/diff?path=&previousPath=` | "Load full diff" for a file GitHub sent NO patch for (CLICK-GATED) → `PrFileFullDiffResponse {path, patch, refused}`. Reads the merge base (at `previousPath ?? path`) and the head, then diffs them server-side with the conflict resolver's Myers engine (`conflict/diff.ts`) into a header-less unified patch — the shape `PrFileDiff.patch` has. A 404 side is empty (added/deleted file); both missing → `missing`; either side binary → `binary`; either over ~1 MB → `too_large`. `patch: ''` = line-identical sides. Up to 4 REST calls cold. Rate tier `[pr_detail, read]` |
| `GET /api/prs/:id/merge-options` | what the merge control needs, fetched LAZILY (the hot detail path must not wait on GitHub): repo-allowed methods + live mergeability + `mergeQueue` (null unless the base branch really has one — `enabled:false` would make every repo render a queue section) + `autoMerge{allowedByRepo,armed}`. The queue probe is `.catch(() => null)` — best-effort, never fails the control. `mergeQueue.entryState` (optional) is the entry state through the ONE normaliser (`mergeQueueEntryStateFrom`), null when not queued, so the client never re-spells GitHub's raw enum. ⚠ **A NON-NULL probe STAMPS the synced queue columns** (`in_merge_queue` / `merge_queue_entry_state`, via `db/pr-merge-queue-stamp.ts`), raising the PR change signal when the stored value moved — NON-FATALLY: this route is a read, and a failed local write never fails it. A failed probe (null) writes nothing, because "we never asked" is not "not queued". It also carries **`reviewDecision`** (the live one, off that same probe, at zero extra cost — see docs/MERGE-CI-TRUNK.md § Why a blocked PR is blocked): ⚠ three states, and the key is OMITTED when the probe failed, because "we never asked" must not arrive as the `null` GitHub uses for "this base requires no review". Up to five upstream calls, so it shares the `prDetail` rate-limit tier with `GET /api/prs/:id` (and `…/files`) |
| `POST · DELETE /api/prs/:id/merge-queue` | enqueue / dequeue on **GitHub's native merge queue** → `MergeQueueResult`. WRITE+ re-checked; enqueue pins the LIVE head sha (same consent anchor as a merge), 400s when the base branch has no queue (rather than failing opaquely inside GraphQL), and is idempotent both ways. GraphQL-only — see `github/mutations.ts`. **Both verbs stamp the synced queue columns** (enqueue: `true` + the normalised entry state, "queued, state unknown" when GitHub's payload carried none; dequeue: `false`/`null`), NON-FATALLY — once GitHub has accepted the mutation the route answers success, or a 502 would invite a second enqueue. ⚠ **DELETE probes `fetchMergeQueueState` FIRST**, because "Remove from queue" now renders on the collapsed merge row from synced columns that can be minutes old: GitHub says not queued ⇒ stamp `false` and answer `{inQueue:false}` WITHOUT calling dequeue; the probe says the PR MERGED (and the local row is still open) ⇒ record the landing instead (`markPrMergedLocally`, which also clears both queue columns, merger null until the next walk, then `noteMergeLanded`); a failed probe falls through to the mutation as before |
| `POST · DELETE /api/prs/:id/auto-merge {mergeMethod,updateStrategy?}` | arm / disarm Pierre's own **"merge when ready"** → `ArmedMergeRequest` · 204 (idempotent). Arming re-checks WRITE+, refuses a non-open PR (409), pins the LIVE head sha (never the synced one — a stale pin disarms itself on the first tick), 409s `StaleBase` when the synced base ref no longer matches GitHub's, and probes the merge queue (best-effort): a queue on the base ⇒ the intent is stamped `viaMergeQueue` (the watcher ENQUEUES instead of direct-merging), a PR already IN the queue ⇒ 409 `AlreadyQueued` (it is already landing). Disarm with the watcher's own queue entry live (`enqueuedAt` set) also best-effort dequeues it — "cancel" must not leave the queue to land the PR anyway; the row is deleted FIRST so the cancel wins even if the dequeue fails. TTL 72h. The arm response is the FULL row (identity + `phase:'pending_first_check'`), so the SPA can seed its progress card on the click rather than on the next poll. The arm's queue probe STAMPS the synced queue columns whenever it answers, the `AlreadyQueued` 409 included (the reader pressed "Merge when ready" because their screen did not know the PR was queued); a disarm whose dequeue GitHub accepted stamps `in_merge_queue: false`, and its warning is logged only when the dequeue itself failed. Both stamps are non-fatal |
| `POST /api/prs/:id/merge {method}` | merge now → `MergePrResult`. WRITE+ re-checked (403 `NotPermitted`); a LIVE conflict pre-check refuses a conflicting PR with **409 `Conflicts`** before GitHub would 405; the merge is pinned to the live head (409 `HeadMoved`, 409 `NotMergeable`, 422 `MethodNotAllowed`). Then `markPrMergedLocally` (which also clears both queue columns) and **`noteMergeLanded`** (`sync/unsettled-prs.ts`): the PR change signal, raised BEFORE the reply, and the TRUNK-MOVED RECHECK — the repo's other open PRs are re-read at ~30s and ~90s, because every one of their merge verdicts now describes a base that no longer exists and none of them bumped `updatedAt` (docs/REALTIME-SYNC.md § Post-write settle). Tier `githubWrite` |
| `POST /api/prs/:id/update-branch {strategy?}` | bring the branch up to date with its base → `UpdateBranchResult {ok, headSha, strategy}`. WRITE+ re-checked; the same live conflict pre-check (409 `Conflicts`), 409 `HeadMoved`, a refused push → 403 `NotPermitted`. A clone-based rebase (default) or merge from trunk, which resolves NOTHING (any conflict aborts → 409 `Conflicts`). ⚠ **IT SETTLES BEFORE IT ANSWERS** — `settlePrAfterWrite` with `headSha` = the pushed sha, an inline wait of ≤~7s, the rest on the settle ladder. It used to stamp and resync nothing, so the board's refetch re-read `behind` and the old head and the Update-branch card came straight back. Response shape unchanged. Tier `githubWrite` |
| `POST /api/prs/:id/ci/rerun {runId, mode}` | re-run a GitHub Actions workflow run → `CiRerunResult`. WRITE+ re-checked (403 `NotPermitted`). Reads the stored `ci_status` BEFORE the rerun, then schedules the settle ladder with `ciNot` = that status when it was `failure`/`error`: CI moves without bumping `updatedAt`, and a stale FAILURE is a known value a ladder with no expectation would stop on at its first read. It follows the red status off for ≤~120s, NOT the run to its finish — the stale-CI backstop and the open PR pane's live poll read that. Tier `githubWrite` |
| `POST /api/dependencies/merge-all?workspace= {prIds, dryRun?}` | Pending → Dependencies' **"Merge or arm all"** → `DependencyMergeAllResponse` (`workspaceId`, `dryRun`, per-PR `items[]`, in request order). Each id is re-checked (this account, the workspace, open, dependency automation by the tab's classifier) — anything else is `skipped: not_found`; drafts, conflicts, no write access, an armed intent and a queued PR are skipped by name. `dryRun` reads synced rows only (`merge` / `arm` / `skipped`) — the confirm dialog. A real run is SEQUENTIAL: queue repo → `armed`; live-ready → `merged` (head-pinned; stamped + `noteMergeLanded`); otherwise or on a "not mergeable" refusal → `armed` (through `armIntentLive`); a failure is that PR's `failed`, never the request's. `maxItems` 100. Tier `github_write` (spelled exactly in `hitsGithub`). Disarming any intent via `DELETE /api/prs/:id/auto-merge` now also records an `auto_merge_policy_skips` row |
| `GET · PUT /api/workspaces/:id/dependency-auto-merge {enabled}` | the per-workspace **"Merge dependency updates automatically"** setting → `WorkspaceDependencyAutoMergeResponse`. OFF by default (NULL). Ownership → 404; `enabled` must be a JSON boolean (checked on the raw body). DB-only (`read`); the sweep that acts on it is server-paced. The SPA now writes the same column through `…/dependency-automation` (below); this route stays for older callers and the demo seed. See docs/MERGE-CI-TRUNK.md § Dependency auto-merge |
| `GET · PUT /api/workspaces/:id/dependency-automation` | **Settings → Dependencies** → `WorkspaceDependencyAutomationResponse` (`settings`: `autoMerge` / `autoApprove` / `autoResolveConflicts` + `policy` `{maxLevel, securityOnly, ecosystems}`; `bots[]`: the workspace's STORED dependency bots with `trusted` and `canRebase`). Every switch OFF by default. Ownership → 404. DB-only (`read`). See docs/MERGE-CI-TRUNK.md § Dependency automation |
| `GET /api/dependencies/automation-log?workspace=` | what the dependency automation did in the workspace's repos in the last 14 days, newest first, ≤ 40 → `DependencyAutomationLogResponse` (`items[]`: `action` approve / rebase_request / ai_resolve, `state` running / done / failed, a one-line `detail`). Fetched only when Pending → Dependencies' "What automation did" is OPENED. DB-only (`read`) |
| `GET /api/auto-merge` | every armed (+ resolved within 24h, cap 200, newest first) intent for the account → `ArmedMergeListResponse`. A pure DB read — the SPA POLLS it for the "it landed" toast and the cross-PR progress stack, so it must never touch GitHub. Each row is SELF-DESCRIBING: `repoOwner`/`repoName`/`prNumber`/`prTitle` (joined, so a global card can label a row without a second request per PR) plus `phase` — the machine-readable twin of the prose `lastReason`, non-null only while ARMED (terminals read `state`; null = a wait the watcher can't characterise). **TRAILING OPTIONALS `queuePosition`/`queueDepth`/`yieldedForFailedChecks`** carry the PER-REPO LANDING ORDER (one intent per `(account, repo)` lands at a time; the rest sit at phase **`queued_local` — Limn's own hold, NOT GitHub's merge queue, which is `queued`**). Derived per request from a second tiny DB scan, never stored — the order changes on every arm/cancel. Absent on terminal rows, on `viaMergeQueue` intents (GitHub owns that order) and when the yield flag is false. See docs/MERGE-CI-TRUNK.md |
| `POST /api/prs/:id/conflicts {autoApply?, restart?}` | **OPEN A MERGE-CONFLICT RESOLVER SESSION** (CORE — `app.ts` registers this family unconditionally and `MeResponse.conflictResolver` is `true`; see docs/MERGE-CI-TRUNK.md § Resolving conflicts in the app). Clones, fetches both refs under `refs/pierre/conflict/<sessionId>` and runs `merge-tree --write-tree` → `202` + `ConflictSession` at `status:'preparing'`; the client watches the stream. ⚠ **ASYNCHRONOUS BY NECESSITY** — Fastify's `requestTimeout` is 60s and a cold `ensureClone` on a large repo blows past it, so everything cheap (ownership, `WRITE_PERMISSIONS`, schema) is validated SYNCHRONOUSLY and refused with a real status code before the 202. ⚠ **`restart:true` is the only way to rebuild against moved shas**; without it the server RE-ATTACHES the live session (`claimSession`), which is what the SPA's refcounted close depends on. ⚠ **`sessionId` IS NOT AN AUTHORISATION TOKEN** — ownership is `getPrWriteContext(prId, accountId)` → 404 on every route in this family — it is a CONCURRENCY token, so a second tab cannot land decisions taken against a model that no longer exists. Nothing here is stored: no table, no migration, no `accountScopedTables()` entry. ⚠ **EVERY FETCH CARRIES THE CALLER'S OWN TOKEN** (`review/clone-manager.ts` `fetchRefIntoClone`) into a session-namespaced ref — the clone cache holds git OBJECTS, never permission. ⚠ **FOUR CAPS, AND THE JOB CAPS ARE NOT THE RECORD CAPS**: `MAX_JOBS_PER_ACCOUNT` (1) + `MAX_CONCURRENT_JOBS` (4) bound concurrent BUILDS and are claimed in a SYNCHRONOUS window — an `await` before the write is the gap where two requests both pass. `MAX_SESSIONS_PER_ACCOUNT` (3) + `MAX_TOTAL_SESSIONS` (24) bound RETAINED records, each holding up to `conflictMaxTotalBytes` (8 MiB) of file text, and are enforced by EVICTING a settled record — unwatched before watched, this account's share first. A 30-min idle TTL and a 4h `MAX_SESSION_LIFETIME_MS` reap the rest. The per-account refusal and the global one are DIFFERENT SENTENCES. ⚠ **THE SPA ALWAYS SENDS `autoApply: false`, ON BOTH OPEN ARMS** — including the re-attach one, because `claimSession` ignores the flag on a live session — and nothing on the client seeds a decision either. The knob stays on the wire; the VALUE the SPA sends is the contract, and dropping the field silently restores auto-apply: the session still opens, the panes still render, the centre pane just quietly arrives pre-decided. ⚠ It is NOT in the model hash and a change to it must NOT bump `CONFLICT_MODEL_VERSION` — see docs/MERGE-CI-TRUNK.md § Resolving conflicts in the app. Rate tier **`sync`** (20/min), the same shape as `POST /api/repos` — NOT `githubWrite` (it writes nothing upstream) and emphatically not the 600/min blanket |
| `GET /api/prs/:id/conflicts?session` | the session MANIFEST — files, counts, the `(headSha, baseSha, modelHash)` pins, `strategies`/`rebaseUnavailableReason`, `prBranchPushable`/`prBranchUnavailableReason`, `reservedBranchNames`. ⚠ **NO REGIONS**: a thirty-file conflict carrying them inline is a multi-megabyte payload on every progress frame. A Map lookup, so rate tier **`read`** — RECORDED, not inherited |
| `GET /api/prs/:id/conflicts/stream?session` | SSE `ConflictSessionEvent` — `snapshot`/`progress`/`ready`/`failed` for the prepare, then `commit_progress`/`commit_done`/`commit_failed` for the push. ⚠ **ONE STREAM CARRIES BOTH**; there is no `…/commit/stream` and no second job registry. Subscribe BEFORE snapshotting so a terminal frame cannot slip through the gap, and check ownership BEFORE `reply.hijack()` (you cannot 404 cleanly after). ⚠ It is a **GET**, so `req.raw.on('close')` IS the correct disconnect signal here — the reply-socket rule is about POSTs. ⚠ **THE SOCKET IS HIJACKED, SO THE SERVER BOUNDS IT**: at most **4 live streams per session** (a 5th is refused `409 Busy` BEFORE the hijack, never queued) and an **absolute 10-minute lifetime** after which the server ends it itself — inside a typical proxy's 15-minute ceiling on purpose, so the close is ours and the SPA's manifest poll is the recovery path that runs. Neither is optional on a `read`-tier route: without them one caller accumulates held sockets and 15-second heartbeat timers in the one server process. ⚠ **CAPPED AND TIME-BOUNDED**: `MAX_STREAM_SUBSCRIBERS` (4) per session → **409 `Busy`**, and `STREAM_MAX_MS` (10 min) ends it server-side. ⚠ **A PROXY MAY CUT IT SOONER**, so on stream error the client FALLS BACK TO POLLING the manifest GET. That poll is the ONLY channel by which a commit pressed after the cut reports its phases, so it must NOT be stopped at `ready`: without it the reader watches “Starting…” forever while the push may already have landed on GitHub. ### Ticket review

One review per TICKET across every PR that names it, separate from the PR review (Claude
Review). Wire types: `packages/shared/src/types.ts` § Ticket review; persistence:
`review/ticket-review/persist.ts`; currency: `review/ticket-review/fingerprint.ts`. Registered
with the other agentic routes (`registerAgenticRoutes`), so absent under `LIMN_AI_DISABLED` (404). Every id-addressed route answers 404 for another account's id.

**Idents.** `jira:<apiRoot>#<KEY>` (a ticket the tracker detected; the same site and key are
the same ticket in every workspace of the account) or `manual:<prId>:<sha8>` (a pasted story,
one PR). Helpers: shared `jiraTicketIdent` / `parseTicketIdent`; the manual hash is
`fingerprint.ts` `manualTicketIdent` (server only). An ident that does not parse → `400
{error:'InvalidIdent'}`.

**Members.** Open and merged PRs on the ticket (`tracker/ticket-source.ts` `ticketMembers`; a manual ident is its
one PR); a closed-but-unmerged PR is dropped. Over `TICKET_REVIEW_MAX_PRS` (30) the run is
REFUSED (`refused: {reason:'too_many_prs', prCount}`), never sampled.

**Contribution cards on the wire.** Every `TicketReviewMember` carries an optional `card?:
TicketPrCard | null` — that PR's contribution card at its CURRENT synced head (which may differ from
the head the run read), or null when there is none at that head: `{headSha, source:
'story_check'|'prepass', createdAt, summary, interfaces: [{kind, name, change, note}], criteria:
[{criterion, how, files}], looseEnds}`. Model-written, verdict-free; server-validated on write and
on read; the stored `changedFiles` never leave the server. Additive and optional: no route changed.
It rides every read that returns a `TicketReview` (`GET /api/ticket-reviews/:id`, `GET
/api/prs/:id/ticket-reviews`). Card availability is NOT part of the currency fingerprint.

**Currency** is server-computed (`deriveTicketReviewState`): the latest SUCCEEDED run's
`fingerprint` = sha256(`TICKET_REVIEW_VERSION` | story hash | sorted `prId:headSha:state`)
against one rebuilt from the synced `pull_requests` heads and the ticket source's current members.
`TicketReviewState.status`: `current` · `stale` (+ `staleBecause` in the order `story_edited`,
`pr_added`, `pr_left`, `pr_pushed`, `pr_merged`, and `changedPrIds`) · `running` (a run is
queued or running; the last succeeded run's counts still ride) · `none`. With no ticket-source answer
the live half is unknown and the latest run reads `current`. A `stale` state may carry `waiting`
(`TicketReviewWait`: `settling` · `ticket_limit` · `daily_limit`) — why the auto sweeper is holding it
back (in memory, `sweep-waits.ts`; absent where auto review is off or nothing waits).
`newComments` (optional) counts the ticket's people comments the latest succeeded run was not given
(`ticket_reviews.comments_seen`); absent / 0 when none or the run predates comment reading. ⚠ Never a
`staleBecause` reason: a comment does not make a run stale or start an automatic one
([TRACKERS.md](TRACKERS.md) § Ticket comments).

review; persistence: `review/ci-review/persist.ts`; currency: `review/ci-review/currency.ts`.
Registered with the other agentic routes (`registerAgenticRoutes`), so absent under `LIMN_AI_DISABLED` (404). Every id-addressed route answers 404 for another account's id. ⚠ No route
returns a log or a log URL: only `CiReviewItem.url`, the check's details page.

**Runs.** One per (PR, head, sorted failing check names), history kept. Every failing check gets
exactly ONE `CiReviewItem` (the `ClaudeCiFailure` shape + `path`, `line`, `suggestion`): `diagnosed`,
or `not_checked` with `notCheckedReason` (`no_log` · `log_unavailable` · `over_cap` ·
`not_reported`). A run that ran no model is `status:'failed'` with `refused` (`no_failures` ·
`no_logs` · `logs_unavailable` · `checks_unreadable` · `head_unreadable`). `counts` (`failing`,
`explained`, `fixableInPr`, `notChecked`) only on a succeeded run. Each item carries `confidence`
(0-100, Claude's; null when not checked or not reported, absent on older runs). `CiReview.autoPost`
(`CiAutoPostWire {status, at, reason, error, postedCount}` | null) says what CI auto-posting did with
an AUTO run — null when it never looked (a manual run, or auto-posting off).

**Currency** is server-computed from the SYNCED head and the newest `ci_status_events` row at it —
no GitHub call. `CiReviewState.status`: `current` · `stale` (+ `staleBecause`: `pushed` ·
`checks_changed` · `now_passing`) · `running` · `none`; `refused` when the newest attempt AT THE
CURRENT HEAD was refused; `checkedAt` = the latest succeeded run's finish.

Automatic runs (`trigger:'auto'`, the sweeper — a failing check on a human PR's synced head in an
auto-enabled workspace, at once, no settle and no CI hold) count against the workspace's
`CI_REVIEW_DAILY_CAP` (default 20, `countAutoCiReviewsSince`); manual runs never do. AI Fix's
review seed reads the `diagnosed` + `fixableInPr` items of the latest succeeded run AT THE PR'S
CURRENT HEAD (`getFixableCiItemsForPr`).
